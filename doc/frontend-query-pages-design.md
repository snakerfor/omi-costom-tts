# 发言人确认页与对话记录查询页设计

## 目标

补两个管理页面，解决两件事：

1. 查询当前哪些发言人还没有确认姓名和身份，并完成确认。
2. 查询历史对话记录，支持按发言人姓名、时间范围等条件检索。

这份文档先做信息架构和交互设计，不直接绑定具体前端框架。考虑到当前项目还是纯后端 TypeScript 服务，后续前端可以先用静态 HTML + 原生 JS，也可以单独接 React/Vue。

---

## 当前项目现状

现有数据库和接口已经具备一部分基础能力：

1. `speakers` 表已经有：
   - `id`
   - `name`
   - `status`
   - `display_label`
   - `sample_text`
   - `sample_segment_id`
   - `sample_audio_path`
2. `conversation_segments` 表已经有：
   - `speaker_id`
   - `speaker_name`
   - `text`
   - `absolute_start_time`
   - `absolute_end_time`
3. 已有接口：
   - `GET /speakers`
   - `GET /speakers/anonymous`
   - `POST /speakers/:id/confirm`

当前缺口也很明确：

1. 只有“确认姓名”，没有“确认身份/角色”的字段和接口。
2. 没有“对话记录查询”接口。
3. 没有面向运营或人工校对的前端页面。

---

## 推荐的信息架构

建议做两个一级页面：

1. `发言人确认`
2. `对话记录`

顶部加一个简单导航栏即可：

- Logo / 项目名
- 发言人确认
- 对话记录
- 当前未确认数量徽标

## 页面一：发言人确认

### 页面目标

让用户快速找到“未确认姓名”或“未确认身份”的发言人，并完成确认。

### 页面布局

建议采用左右分栏：

1. 左侧为筛选栏 + 发言人列表
2. 右侧为发言人详情与确认表单

### 左侧区域

包含以下内容：

1. 搜索框
   - 支持输入显示名、已确认姓名、临时标签
   - 示例：`张三`、`未命名发言人1`
2. 状态筛选
   - 全部
   - 未确认姓名
   - 未确认身份
   - 全部未确认
   - 已确认
3. 时间范围筛选
   - 最近 24 小时
   - 最近 7 天
   - 最近 30 天
   - 自定义开始/结束时间
4. 列表项字段
   - 显示标签，例如 `未命名发言人3`
   - 已确认姓名，没有则显示 `未确认`
   - 身份标签，没有则显示 `未确认`
   - 最近出现时间
   - 出现会话数
   - 语音片段数
   - 样本文本摘要

### 右侧详情区域

点击左侧某个发言人后展示详情：

1. 基本信息卡片
   - 发言人 ID
   - 当前状态
   - 首次出现时间
   - 最近出现时间
   - 出现会话数
   - 片段数
2. 样本音频
   - 播放按钮
   - 时长
   - 音频来源会话
3. 样本文本
   - 展示 3 到 5 条代表性片段
4. 最近对话轨迹
   - 展示最近几次出现在哪些会话
   - 每条可以跳转到“对话记录”页面
5. 确认表单
   - 姓名输入框
   - 身份输入框
   - 备注输入框，可选
   - 保存按钮
   - “仅确认姓名”按钮，可选

### 建议交互流

#### 场景 A：确认姓名和身份

1. 用户打开页面，默认落在“全部未确认”。
2. 左侧列表展示所有待处理发言人，按最近出现时间倒序。
3. 用户点击某个发言人。
4. 右侧显示该发言人的样本文本和样本音频。
5. 用户填写：
   - 姓名，例如 `张三`
   - 身份，例如 `客户`、`销售`、`面试官`
6. 点击保存。
7. 列表立即更新状态，并从默认待处理列表中消失或标记为已确认。

#### 场景 B：只先确认姓名

1. 用户先填姓名，不填身份。
2. 状态变为“姓名已确认，身份待确认”。
3. 后续可再次补录身份。

### 页面状态建议

列表状态建议不要只用一个 `status` 字段覆盖全部含义，而是拆成两个布尔维度：

1. `name_confirmed`
2. `identity_confirmed`

然后页面展示状态标签：

1. `待确认`
2. `仅姓名已确认`
3. `已完成确认`

## 页面二：对话记录查询

### 页面目标

支持人工查看历史会话内容，按发言人姓名或时间范围快速定位记录。

### 页面布局

建议采用上下结构：

1. 上方是检索条件区域
2. 下方左边是会话列表
3. 下方右边是当前会话详情与逐段 transcript

### 检索条件区域

建议字段如下：

1. 发言人姓名
   - 支持模糊查询
   - 可输入已确认姓名，也可搜未命名标签
2. 身份
   - 例如客户、销售、老师、学生
3. 时间范围
   - 开始时间
   - 结束时间
4. 会话状态
   - completed
   - failed
   - recording
5. 关键词
   - 在 `conversation_segments.text` 中搜索
6. 是否包含未确认发言人
   - 全部
   - 仅包含未确认
   - 仅全部已确认

### 会话列表字段

每条会话建议显示：

1. 会话 ID
2. 开始时间
3. 结束时间
4. 总时长
5. 发言人数
6. 已确认人数 / 未确认人数
7. 文本摘要前 1 到 2 句
8. 状态标签

### 会话详情区域

点击某条会话后，右侧展示：

1. 会话基础信息
   - 会话 ID
   - Session ID
   - UID
   - 开始时间
   - 结束时间
   - 时长
   - 音频文件链接
2. 参与发言人概览
   - 发言人姓名
   - 身份
   - 发言段数
   - 总发言时长
3. Transcript 时间轴
   - 每条段落显示：
     - 发言人展示名
     - 身份标签
     - 开始/结束时间
     - 文本内容
     - 置信度
   - 如果该发言人未确认，显示醒目标识，并提供“去确认”按钮
4. 快速筛选
   - 只看某一个发言人
   - 只看未确认发言人

### 建议交互流

#### 场景 A：按发言人查历史记录

1. 用户输入 `张三`。
2. 系统返回所有包含 `张三` 发言片段的会话列表。
3. 用户点开某个会话。
4. 右侧 transcript 自动高亮 `张三` 的发言段。

#### 场景 B：按时间范围查最近会话

1. 用户选择最近 7 天。
2. 系统返回这段时间内所有已完成会话。
3. 用户点击某会话后查看完整 transcript。

#### 场景 C：在 transcript 中发现未确认发言人

1. 用户在会话详情中看到 `未命名发言人2`。
2. 点击“去确认”。
3. 右侧弹出确认抽屉，或者跳转到“发言人确认”页并定位当前发言人。

## 关键数据模型调整建议

为了支持“身份确认”，建议扩展 `speakers` 表，而不是把身份硬塞到 `name` 或 `display_label`。

### 推荐新增字段

给 `speakers` 表增加：

1. `identity_label TEXT`
   - 人工确认身份，例如 `客户`、`老师`、`同事`
2. `identity_status TEXT`
   - `unconfirmed` / `confirmed`
3. `notes TEXT`
   - 补充备注
4. `first_seen_at TEXT`
   - 首次出现时间，便于排序和查询
5. `last_seen_at TEXT`
   - 最近出现时间

给 `conversation_segments` 表增加：

1. `speaker_identity TEXT`
   - 查询 transcript 时避免频繁 join，也方便保留历史快照

### 推荐的状态表达

不要只依赖当前的 `speakers.status` 一个字段来表达全部状态。建议：

1. `status` 继续保留，表示发言人的总体状态，例如 `anonymous` / `confirmed`
2. 新增：
   - `name_confirmed INTEGER`
   - `identity_confirmed INTEGER`

如果不想一次性改太多，也可以先用：

1. `name IS NOT NULL` 代表姓名已确认
2. `identity_status = 'confirmed'` 代表身份已确认

## 推荐后端接口

### 发言人管理接口

#### 1. 查询发言人列表

`GET /api/speakers`

查询参数建议：

1. `q`
2. `confirmation`
   - `all`
   - `unconfirmed_name`
   - `unconfirmed_identity`
   - `unconfirmed_any`
   - `confirmed`
3. `start_time`
4. `end_time`
5. `page`
6. `page_size`

返回字段建议：

1. `id`
2. `display_label`
3. `name`
4. `identity_label`
5. `name_confirmed`
6. `identity_confirmed`
7. `status`
8. `first_seen_at`
9. `last_seen_at`
10. `conversation_count`
11. `segment_count`
12. `sample_text`
13. `sample_audio_path`

#### 2. 查询单个发言人详情

`GET /api/speakers/:id`

返回：

1. 发言人基础信息
2. 最近会话列表
3. 代表性片段
4. 样本音频

#### 3. 更新发言人确认信息

`PATCH /api/speakers/:id`

请求体建议：

```json
{
  "name": "张三",
  "identityLabel": "客户",
  "notes": "由运营人工确认"
}
```

#### 4. 获取待确认统计

`GET /api/speakers/stats`

返回：

```json
{
  "unconfirmedName": 3,
  "unconfirmedIdentity": 5,
  "unconfirmedAny": 6
}
```

### 对话记录接口

#### 1. 查询会话列表

`GET /api/conversations`

查询参数建议：

1. `speaker_name`
2. `identity_label`
3. `keyword`
4. `start_time`
5. `end_time`
6. `status`
7. `has_unconfirmed_speakers`
8. `page`
9. `page_size`

#### 2. 查询会话详情

`GET /api/conversations/:id`

返回建议包含：

1. 会话基础信息
2. 参与发言人摘要
3. transcript segments

#### 3. 查询 transcript 片段

如果后续要做无限滚动或大数据量分页，可以增加：

`GET /api/conversations/:id/segments`

## 页面字段映射建议

### 发言人确认页

左侧列表字段映射：

1. 标题：`name || display_label`
2. 副标题：`identity_label || "身份未确认"`
3. 标签：
   - `name ? "姓名已确认" : "姓名未确认"`
   - `identity_label ? "身份已确认" : "身份未确认"`
4. 时间：`last_seen_at`
5. 摘要：`sample_text`

### 对话记录页

会话列表摘要字段：

1. 时间：`conversations.first_audio_frame_at || conversations.created_at`
2. 状态：`conversations.status`
3. 摘要：取前几条 `conversation_segments.text` 拼接
4. 发言人统计：按 `speaker_id` 聚合

transcript 行字段：

1. 发言人：`speaker_name || speakers.display_label || speaker_label`
2. 身份：`speaker_identity || speakers.identity_label`
3. 时间：`absolute_start_time` 到 `absolute_end_time`
4. 文本：`text`

## 视觉设计建议

整体建议偏“运营后台”风格，重点是信息密度和操作效率，不要做成重装饰型页面。

### 颜色

1. 主色建议用蓝绿系，强调“识别/确认”状态。
2. 未确认状态用橙色或红色标签。
3. 已确认状态用绿色标签。

### 组件

建议优先准备这些通用组件：

1. 顶部导航
2. 筛选栏
3. 数据表格或列表
4. 详情抽屉 / 右侧详情面板
5. 标签 Tag
6. 时间范围选择器
7. 音频播放器
8. transcript 时间轴

### 响应式建议

桌面端优先，移动端不建议承载完整管理操作。

桌面端：

1. 发言人确认页用双栏
2. 对话记录页用“三块布局”

窄屏端：

1. 列表在上
2. 详情折叠到抽屉

## 分阶段实现建议

### 第一阶段

先把后端查询能力补齐：

1. `GET /api/speakers`
2. `GET /api/speakers/:id`
3. `PATCH /api/speakers/:id`
4. `GET /api/conversations`
5. `GET /api/conversations/:id`

### 第二阶段

先做最小可用前端：

1. 一个静态管理页面
2. 两个 Tab
3. 发言人列表 + 详情确认
4. 对话记录列表 + transcript

### 第三阶段

再补体验优化：

1. 分页
2. 高亮关键词
3. “去确认”联动跳转
4. 音频片段试听
5. 批量确认

---

## 结论

这两个页面是合理且必要的，但如果要完整支持“确认姓名 + 确认身份”，当前后端至少要先补两类能力：

1. `speakers` 的身份字段和更新接口
2. `conversations / conversation_segments` 的查询接口

页面上建议先做：

1. 一个“发言人确认页”，专注处理待确认对象
2. 一个“对话记录页”，专注检索和回看 transcript

如果下一步开始实现，建议先从后端接口和一个简单静态后台页面起步，这样改动最小，也最适合当前仓库结构。
