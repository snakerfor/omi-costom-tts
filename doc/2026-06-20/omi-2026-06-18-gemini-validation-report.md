# OMI 2026-06-18 Gemini 验证报告

## 1. 目的

用 Gemini 3.1 Pro Preview 对 2026-06-18 的 OMI 桌面数据做一次样本验证，检查这套方案能不能从原始音频、视频 chunk、截图和窗口上下文里挖出有意义的日常活动。

## 2. 输入事实

本次验证使用的事实如下：

- 音频上传：`74` 个 wav，时间大致覆盖 `06:30` 到 `21:04`
- 视频 chunk：`193` 个
- 截图：`3699` 条
- OCR 非空：`327`
- OCR 为空：`3372`
- 转写会话：
  - `2026-06-18 01:00:59.653`，`recording`，`source=desktop`
  - `2026-06-18 11:50:53` 到 `11:53:22.560`，`completed`，标题是“英语词汇与春天事物认读”
- 代表性截图：
  - Omi Local / Rewind / Memories / Tasks / Dashboard
  - Google Chrome 打开 “VibeVoice 说话人分离能力 - Google Gemini”
  - Codex 窗口里可见 `audio-uploads`、`raw results`、`finalized results`、`omi-videos`、`screenshots`、`omi-sync-agent`
  - System Settings / Storage 显示磁盘接近满

## 3. Gemini 输出摘要

Gemini 的判断大致是：

- 这一天的核心活动是本地开发、调研和设备数据流管理
- 能从截图、窗口标题、OCR、音频连续性里重建有意义的事件边界
- 用户很可能在调研语音分离与多模态数据链路
- 中午有一段很短的英语认读学习/教学内容
- 当前存储设计偏紧张，长期看需要更强的检索层

它给出的几个关键点是对的：

- 识别出了 `Codex + audio-uploads + omi-videos + screenshots + omi-sync-agent` 这一类开发场景
- 识别出了 Chrome 里的 Gemini / VibeVoice 调研线索
- 注意到了系统磁盘几乎满
- 认可“视频 chunk + 截图 + 窗口标题 + OCR + 音频连续性”可以做事件重建

## 4. 我的校验判断

### 4.1 可靠的部分

Gemini 对“当天主要是开发和调研”这个结论，和现有证据是对得上的。

尤其是：

- Codex 窗口确实暴露了项目目录和同步链路
- Chrome 窗口确实在看语音分离 / Gemini 相关内容
- `omi_transcription_sessions` 里确实有一条短学习会话

### 4.2 需要保守看待的部分

Gemini 有几处属于“合理推断”，不是硬证据：

- “全天候无人值守”属于趋势判断，不是直接证据
- “职业画像”属于推测，只能当辅助描述
- “凌晨 1 点启动录制”可以从会话记录看到，但其具体原因不能硬下结论

### 4.3 OCR 空白的解释

它把大量空白 OCR 解释成“页面无文字 / 纯布局 / OCR 识别率低”，这和我们的观察一致。

所以结论不是“数据坏了”，而是：

- OCR 本身只提供文字
- 对代码页、设置页、纯布局页，它天然就会弱
- 想知道页面在干什么，必须结合窗口标题和画面上下文

## 5. 结论：这套方案能挖出什么

按现在的方案，已经可以挖出三类结果：

1. 日内活动轮廓
   - 什么时候在开发
   - 什么时候在调研
   - 什么时候在学习
   - 什么时候在系统维护

2. 任务级事件
   - 某段时间是在看什么项目
   - 某段时间是在研究什么技术
   - 某段时间是在处理什么本地数据

3. 生活/工作结构
   - 哪些时间段持续高强度
   - 哪些窗口切换最频繁
   - 哪些任务反复出现

但它还不够强到直接替代人工复盘。  
原因是空白 OCR 很多，细粒度语义仍然需要：

- 视频帧回看
- 窗口标题补语义
- 音频/转写补上下文

## 6. 当前存储够不够用

### 6.1 现在够用的场景

如果目标还是下面这些，当前“文件 + 关系表”的方式基本够：

- 按天回看
- 精确查某个时间点
- 统计截图数、音频数、视频 chunk 数
- 复现当天任务边界
- 做日总结

### 6.2 什么时候需要向量数据库

当你开始做下面这些事情时，向量数据库就会变得有价值：

- 跨天模糊检索
- 按语义找相似事件
- 找“我什么时候研究过某个技术”
- 把 OCR、窗口标题、转写、总结统一做语义召回
- 做月度/季度级别的二次挖掘

### 6.3 什么时候还不必上向量库

如果只是：

- 先把每天的原始数据整理清楚
- 先做精确时间线
- 先做结构化摘要

那暂时不必重构成大而全的向量方案。

## 7. 建议的技术路径

我的建议是分两步：

1. 先保留现有结构
   - 文件系统存原始音视频
   - SQLite / Postgres 存元数据、摘要、事件边界、日总结

2. 再补向量层
   - 先向量化“高价值文本”
   - 包括有效 OCR、窗口标题、转写、日总结
   - 不要先把海量空白截图硬向量化

这样比一开始就重搭框架更稳。

## 8. 最终判断

这次验证说明：

- 方案是可行的
- 已经能从 6 月 18 日里挖出明确的工作/调研/学习轮廓
- 当前数据存储结构足以支撑“按天验证”和“精确回放”
- 向量数据库更适合第二阶段，用于跨天语义检索和二次挖掘

换句话说：

- **现在**：不用重构框架，先补表和补摘要就够
- **以后**：当你要做跨天、模糊、相似语义检索时，再上向量库
