# 三阶段执行计划

本文用于承接 2026-04-10 这轮讨论后的执行顺序，只保留后续最值得投入的主线任务，避免并行做太多方向导致样本污染和链路复杂化。

## 阶段一：先稳定单场会话里的 speaker 归属

目标：

- 优先解决同一真实人被拆成多个 speaker
- 优先解决不同真实人被并到同一个 speaker
- 优先解决说话切换时前一两句“黏连”到上一个人的问题

建议做法：

- 保留 Soniox realtime 作为实时文本主链路
- 引入 pyannote 作为 speaker 层纠偏能力
- 使用 `Soniox text + pyannote diarization + 时间对齐/时序平滑` 作为新的 speaker 归属主方案
- 对极短片段、低重叠片段、边界片段增加 `uncertain` 或平滑规则，避免硬归属

验收标准：

- 同一 session 中最终 speaker 数更接近真实人数
- 管理平台里 speaker 列表稳定，不再出现明显的 1 人多 ID 或多人 1 ID
- 开头 speaker 切换时的误归属明显下降

为什么先做这个：

- 这是当前最直接影响结果可信度的问题
- 如果这一层不稳，后面的样本、embedding、identity 库都会被污染

## 阶段二：做云端 VAD / 静音门控，先解决成本和无效处理

目标：

- 减少大量静音音频进入实时 STT
- 降低 Soniox 流式时长成本
- 减少无意义片段和长时间空跑

建议做法：

- 不假设手机端或硬件端已做强静音过滤
- 在当前 WebSocket 服务端增加轻量 VAD / 静音门控
- 保留完整原始 WAV 归档，不修改归档时间轴
- 只控制“哪些 chunk 发给 Soniox”
- 加入前卷和后卷缓冲，避免截断句首句尾

建议顺序：

- 先做统计和日志观察
- 再做保守阈值版本
- 最后再评估是否继续激进收紧阈值

验收标准：

- 单 session 的 Soniox 实时处理时长明显下降
- 长静音期间不再持续消耗实时流
- 文本和 speaker 效果没有明显恶化

为什么排第二：

- 这项主要解决成本和效率
- 它重要，但不是当前 speaker 错乱的主因

## 阶段三：再做跨会话 speaker identity / voice profile

目标：

- 支持跨 session 识别同一个真实人
- 为管理平台提供更稳定的人物归档与人工确认能力

建议做法：

- 在阶段一稳定后，再正式建立 enrollment 样本策略
- 区分 `enrollment sample` 和普通 observation sample
- 确认服务器上的 embedding 产出是真实声纹，而不是 fallback 向量
- 建立 speaker profile，而不是只存一条代表 embedding
- 对已确认 speaker 采用更保守的更新和覆盖规则

验收标准：

- 同一已确认 speaker 在多场会话中能稳定复用
- identity 库不因低质量样本发生明显漂移
- 管理平台中的人工确认结果可长期复用

为什么排第三：

- 这项依赖前两阶段的数据质量
- 如果 speaker 归属不稳、静音样本过多，identity 库会快速被污染

## 当前优先级结论

当前推荐优先级：

1. 阶段一：speaker 稳定性
2. 阶段二：云端 VAD / 静音门控
3. 阶段三：跨会话 identity / voice profile

一句话总结：

- 先把“这场会话里谁在说话”做对
- 再把“静音别白白花钱”做好
- 最后再做“这个人是谁”的长期身份库
